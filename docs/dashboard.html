Rung Ladder

Six rungs from a HuggingFace baseline to paged attention and prefix caching, each built only after the one below it produced a number and a correctness proof. The proof is always the same: token-identical output under greedy decoding. Not similar — identical.

⚠
Measured on two platforms: a MacBook (Apple Silicon, MPS) and a Tesla T4 (Kaggle, CUDA). Each section says which. They do not agree, and where they disagree the GPU is right — four conclusions drawn on Apple Silicon turned out to be artifacts of that platform, including one this project treated as central.

The gap is not where this project spent five rungs predicting it would be

Throughout, the gather was logged as the largest expected line item: Inferno materialises a contiguous K/V tensor from the block table every layer, every decode step, where vLLM’s kernel walks the block table internally and never materialises. It was written down as the answer twice before any GPU existed to test it.

R1 has no block table and no gather at all — and is already 4.49× behind. The gap is fully present before paging is introduced, so paging cannot cause it. At equal concurrency the paged engine actually ran 2% faster than the contiguous one.

The real answer is in the grouping: Inferno (38.88) and HuggingFace (31.76) sit within 22% of each other, and vLLM is 4.5× both. The difference is not something Inferno does badly — it is something neither does at all: CUDA graph capture (vLLM replays one captured graph where Inferno dispatches ~360 kernel launches per step from Python), ahead-of-time compilation, and a fused attention kernel. What the GPU destroyed

Every rung was first measured on Apple Silicon. Four conclusions did not survive CUDA. All four were measured carefully, reproduced, and written down with confidence — they were properties of one platform mistaken for properties of the technique, and nothing achievable on that platform could have caught it.

Concluded on MPSOn CUDA
Throughput peaks at exactly batch 16 and falls back at 20 — reproducible across three runs Dead. Monotonic 1→32: 38.9 → 214 → 644 tok/s. An MPS kernel artifact.
“The textbook batching argument does not hold here” — batching bought ~8% from batch 1 to 8 Dead. 5.5× from 1→8, 16.6× at 32. The argument holds fine; MPS was the problem.
Block size 16 is clearly best (146 vs 115/139 tok/s), matching vLLM’s default Dead. Nearly flat across 4/16/64, and 16 is the slowest. bs=4 gives 97.2% utilisation and full concurrency.
Prefix caching cuts TTFT 4.89× Overstated. 1.44×. Prefilling 485 tokens costs a T4 ~42 ms — there is little to save. The value of prefix caching is proportional to how expensive prefill was.

What survived: head-of-line blocking at 17.9% of decode steps on both platforms (a property of the policy, not the hardware); continuous batching’s advantage, which grew from 5.3× to 16×; paging’s concurrency advantage, 8× → 9.1×; and the prefix cache hit rate, 83.8% on both.

R2 — static batching, and why it is not enough (Apple Silicon)

A static batch runs until every sequence in it finishes. A request needing 8 tokens sits through all 128 steps, producing nothing and holding its cache slot. Prompts are not sorted by length — sorting would flatten the tail and hide the effect this rung exists to demonstrate.

Head-of-line blocking — every request at batch size 8

Decode steps each request spent in the batch after producing its last token, sorted descending. ~18% of all decode steps compute tokens that are thrown away; the worst-hit request waits 120 steps. No batch size fixes this — it gets worse as batch size grows, because the cause is structural. This chart is the argument for R3.

Throughput vs batch size

The textbook argument says batching decode is nearly free, since weights load once per step regardless of batch size. It does not hold here: batch 1→8 moves 28.30→30.53 tok/s, about +8%. Then batch 16 triples it and batch 20 falls back — reproducible across three runs, and still unexplained (B5).

R3 — continuous batching under real arrivals

Every earlier benchmark assumed all prompts exist at t=0, which is the one assumption under which continuous batching has nothing to show. This replays a Poisson arrival schedule against both schedulers. The static baseline is R2’s policy made arrival-aware: take whatever has arrived, run it to completion, then look again.

TTFT p95 vs arrival rate

Budget is p95 TTFT under 500 ms (dashed). Static misses it from 0.4 req/s; continuous holds to 1.6. Raw throughput barely differs — the win is entirely in latency, which is the correct shape: continuous batching does not make the hardware faster, it stops requests waiting on strangers.

R4 — paged KV cache

R3 gave every sequence a contiguous reservation of max_len, so concurrency was budget / (max_len × bytes_per_token) — fixed in advance, independent of how long sequences actually are. This workload averages ~77 tokens against a 525-token reservation, so 84% of the reserved cache never holds a token. Paging hands out fixed-size blocks on demand, bounding waste to block_size − 1 per sequence.

Same 48 MB, how many sequences fit

The headline. Throughput follows from the extra concurrency, not from paging being faster per step.

Block size: waste against gather cost

Small blocks waste least but multiply bookkeeping and gather work; large blocks gather cheaply but strand up to block_size − 1 tokens per sequence. 16 wins here — also vLLM’s default, but the number came from this table.

R5 — prefix caching

Attention is causal, so position i’s K/V depend only on tokens 0–i. Two sequences starting with identical tokens have bit-identical KV across that span — so the blocks are shared, not recomputed. Workload: 15 prompts sharing one ~2000-character document, each asking a different question. A/B on the same engine with only the cache toggled.

Prefill work, and what it costs

85.3% of all prefill tokens are never computed. This is the only rung whose win is in avoided work rather than better scheduling or packing, which is why it is the largest single speedup measured.

The limit, measured from two directions

A cache hit computes ~8.7% of the prompt’s tokens but still takes ~23% of a cold prefill. The saving lands on the projections, the MLP and the attention math — the gather is unchanged: every layer materialises the whole block table regardless of how much was cached. R4 showed the same ceiling from the other side, where paging at equal concurrency was ~8% faster than contiguous, because the contiguous baseline gathers too. A fused PagedAttention kernel is what removes this, and it is the single largest expected line item in the gap analysis.

Still open

The 4× is named but not decomposed

Four causes identified and ranked by argument — graph capture, compilation, fused attention, chunked prefill. No profiler was run, so that ranking is reasoned rather than measured. Nsight or torch.profiler would settle it.

One GPU, one model, one session

Tesla T4, 0.5B parameters. A 7B model on an A100 would move every ratio here. And the four MPS conclusions that died are a standing warning against trusting any of these numbers on a third platform without re-measuring.

B4R2 batch parity failed at batch size 4 while passing at 1 and 2 — one sequence emitting token 0 forever, another drifting after 67 exact tokens.The additive mask used finfo.min. float16’s most negative finite value is −65504, so adding any score past about −16 rounds off the end of the range to −inf; scores reach ±225 by layer 8. B6The scheduler assigned a slot only after deciding to prefill a request.The engine needs the slot to write K/V into before it can run the forward pass — the scheduler was unusable by the thing it existed to drive. First bug in the project caught by a unit test rather than a benchmark: 0.01 s instead of minutes.resolved
B7R4 test suite ran 600 s with no output, no error and no progress.A livelock. preempt() returned victims to the front of the queue so they would not starve, and FCFS admission only considers the head — so the victim was re-admitted and immediately re-evicted, forever. Two individually correct rules composing into a cycle. Not starvation: both requests were repeatedly admitted, they just never held memory long enough to emit a token.resolved
B8The R4 benchmark reported 126% cache utilisation.The metric divided total tokens across all served requests by n_slots × max_len, correct only when every request holds a slot at once. On 56 requests through 7 slots it over-counted ~8×. Corrected: R3’s real utilisation is 15.8%, not 39.0% — the error flattered the baseline.resolved
B9pytest tests/ ran 25 minutes with no output.Not hung — swapping. 48 MB RSS at 11% CPU with system swap at 6.9 GB of 8 GB. Every test file holds its engine in a session-scoped fixture, so one pytest session keeps ~5 model copies resident on a machine that holds about two. A swapping process looks exactly like a working one.resolved
B10The test runner could report a failing file as green.It extracted pytest’s summary with tail -2 | head -1, then grepped that line for failures. Files printing from inside tests interleave with the progress dots, so the captured line was not the summary. Unlike B8 this failed silently toward green, which in a test runner is strictly worse.resolved

Open questions

What does the gather cost against a fused kernel? blocks the gap analysis
Both the paged and contiguous caches materialise, so every comparison so far measures one gather against another. The number that matters needs vLLM on GPU.
Why does throughput peak at exactly batch 16? open
Per-step cost halves at 16 while the work doubles, then reverts at 20. Next test: sweep 13–18 with fixed-length prompts so composition is held constant.
Why is Inferno’s prefill 1.8–4.6× slower than HuggingFace’s eager path?open
Four candidates, none measured: a fresh mask tensor every forward; repeat_kv materialising a 7× copy of K and V; cos/sin recomputed per forward; fp32 softmax over a 14×475×475 tensor. Profile before touching any of it.
Does preemption need a watermark? low priority
8 preemptions across 56 requests — low enough not to matter here. The livelock fix guarantees progress but does not prevent thrashing under heavier pressure.
