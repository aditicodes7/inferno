R1 — hand-written engine vs HuggingFace

Inferno uses eager attention, so the honest like-for-like comparison is against HuggingFace’s eager path. HF’s fused SDPA kernel is shown too, because that is what HuggingFace actually runs by default and pretending otherwise would flatter Inferno.

Prefill, measured. Inferno wins on decode and loses badly here — and the p95 gap is dominated by the 475-token RAG prompts. This is the first genuine performance gap of the project.

Decode throughput by prompt length

Same model, same settings; the only difference is context length. Long prompts decode slower for every implementation — that is the KV cache getting more expensive to read on every single step, showing up unprompted in the baseline.

R2 — static batching, and why it is not enough

A static batch runs until every sequence in it finishes. A request that needed 8 tokens sits in the batch for all 128 steps, producing nothing, holding its cache slot, and not returning to the caller. Its latency is set by the slowest request it happened to be batched with. Prompts are not sorted by length — sorting would flatten the tail and hide the effect this rung exists to demonstrate.

Head-of-line blocking — every request at batch size 8

Decode steps each request spent in the batch after producing its last token, sorted descending. At batch 8 and above ~18% of all decode steps compute tokens that are thrown away, and the worst-hit request waits 120 steps: it finished in 8 and was delivered after 128. No batch size fixes this — the numbers get worse as batch size grows, because the cause is structural. This chart is the entire argument for R3.

Throughput vs batch size

The textbook argument says batching decode is nearly free, because the weights are loaded once per step regardless of batch size. It does not hold here: from batch 1 to 8, throughput moves 28.30 → 30.53 tok/s, about +8%. Then batch 16 triples it and batch 20 falls back — a reproducible, isolated peak measured at 96.96, 97.06 and 99.42 tok/s across three runs, and still unexplained (B5).

Why R4 exists

R1’s cache preallocates prompt_len + max_new_tokens and never grows, so every sequence reserves for its worst case. Verified linear at exactly 12,288 bytes per token — matching 2 × 24 layers × 2 KV heads × 64 head_dim × 2 bytes.

KV utilisation per request, all 50 prompts

Fraction of reserved cache actually holding a real token, sorted ascending. The mean of 85.8% flatters the design: 35 of 50 prompts ran the full 128 tokens, so there was little early termination to waste reservation on. The left tail is the real cost.

Bugs worth the writeup

IDWhat brokeMechanismStatus
B1 sdpa and eager produced different tokens from identical inputs — 10/50 prompts, one diverging at generated token 1. Fused kernels accumulate in a different order; float addition is not associative. Greedy decoding turns a 1-ulp difference into a different paragraph once argmax flips on a near-tie, and the two sequences never re-converge. property, not a defect
B2 TTFT p95 of 297 ms that would not reproduce — later runs gave 88 ms. TTFT was not monotonic in prompt length. Outliers followed neither the prompt nor its position in the run; they appeared only in the first process ever run on the machine. Leading explanation is persistent on-disk Metal shader caching — not directly proven. resolved — methodology
B3 R1 parity failed 49/50. Fluent output, no crash, up to 34 exactly-matching tokens before diverging. The checkpoint ships repetition_penalty: 1.1, and HuggingFace applies it in greedy decoding — it is not gated on do_sample. The hand-written forward pass was correct throughout: teacher-forced agreement was 371/371. “Greedy” is not a complete specification of a decoding procedure. resolved
B4 R2 batch parity failed at batch size 4 while passing at 1 and 2 — one sequence emitting token 0 forever, another drifting after 67 exact tokens. The additive mask used finfo.min. float16’s most negative finite value is −65504, so adding any score past about −16 rounds off the end of the range to −inf; scores reach ±225 by layer 8. A fully-masked row — which exists only because of left padding — becomes all −inf, and softmax gives exp(−inf − −inf) = NaN. It escaped into real tokens because pad K/V share the cache and 0 × NaN = NaN. Fixed with finfo.min / 2. Two wrong turns first: a probe using a score of −5 (which rounds back, and “proved” no overflow), and a fix that moved the NaN from layer 1 to layer 8 without removing it. resolved
B5 Throughput vs batch size is non-monotonic: flat from 1–8, triples at 16, falls back at 20. Reproducible across three runs (±2.5%) and not explained by batch composition — weighted by padded width, batch 16 does more attention work than batch 12 while taking 2.6× less wall time. Leading hypothesis is MPS matmul kernel selection at a 16-wide tile boundary. Not confirmed. open

Open questions

Why is Inferno’s prefill 1.8–4.6× slower than HuggingFace’s eager path?open
Four candidates, none measured: a fresh mask tensor allocated every forward; repeat_kv materialising a 7× copy of K and V at 475 positions; cos/sin recomputed per forward; fp32 softmax over a 14×475×475 tensor. Profile before touching any of it.
Should the parity criterion be hardware- and dtype-specific? resolved — two-tier
float32 asserts exact batched-vs-unbatched equality at every batch size: that is the gate on the batching code, and it passes. float16 asserts only that nothing becomes NaN; drift is reported, not asserted, because differently shaped matmuls reduce in different orders and greedy decoding amplifies the last bit. Verified float32 exact at bs 1/2/4/8/16; float16 79/80.
Why does throughput peak at exactly batch 16? open
Per-step cost halves at 16 while the work doubles, then reverts at 20. Next test: sweep 13–18 with fixed-length prompts so composition is held constant. If the dip sits exactly at 16, it is kernel selection. Worth re-running the whole sweep on GPU before drawing any conclusion about batching.
Was the B2 tail actually Metal shader caching? low priority
Never directly proven. Clearing the Metal cache and re-running would settle it.
